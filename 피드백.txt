[한 줄 결론]
  현재 IPC 0.61 (문서와 동일). 사이클의 64%가 "디코드에 들어올 명령이 없는" 상태이고,
  그 원인은 백엔드가 아니라 명령 공급 경로(fetch)다.
    - taken 분기 뒤 fetch 재시작 버블 .......... 사이클의 약 40%
    - 순차 fetch 간극(블록당 4 cycle) ........... 사이클의 약 22%
    - 분기 예측 실패 flush 복구 ................. 사이클의 약 1.7%
  fetch 를 고치면 다음 병목은 D-cache 쓰기 경로(쓰기 1건이 엔진+포트를 7 cycle 점유)로 옮겨간다.
  사본 RTL 에서 7단계 변경으로 같은 ELF 의 IPC 를 0.61 -> 1.21 로 올렸다 (CRC 일치, 쓰기 완료=버스 응답 규칙 유지).
    문서 주측정(10회) O2: 4,896,919 -> 2,446,328 cycles, IPC 0.612 -> 1.225 (CoreMark/MHz 추정 2.04 -> 4.09)
    O3 10회 1.221, 2회(같은 ELF) 1.213, 코드 배치별 1.19~1.22 (정확성 수정 2건 반영 후 최종값, 5b 장 끝 참고)
    Linux 6.12 부팅 재실행에서 이 사본의 결함 2건이 발견되어 수정했다 (PMP 주소, SRAM bridge 읽기 기아). 5b 장 "부팅 회귀에서 발견한 결함" 참고.
    남은 작업: atomic/fence.i/RV32 회귀 전체, 타이밍(Fmax) 평가 (5b 장, 9장 참고)

4. 원인과 RTL 위치
-------------------------------------------------------------------------------------
  (1) fetch 한 블록이 4 cycle 이고 겹치지 않는다
        rtl/soc/rv23_if_translate.sv:42   FSM  IDLE -> TRANSLATE -> ISSUE -> WAIT_DATA -> IDLE
        rtl/soc/rv23_if_translate.sv:50   req_ready_o 는 IDLE 일 때만 -> 응답이 온 뒤 다음 사이클에야 새 요청 수락
        => 16B 를 4 cycle 에 1번. 문서의 진단 "독립 ADDI 1.28 cycle/op" 과 같은 원인.
        이 FSM 은 HAS_MMU=1 일 때만 삽입된다 (rtl/rv_ooo_core.sv:343-345). RV32 빌드(HAS_MMU=0)는 FSM 없이 adapter 로 직결.
  (2) taken 분기마다 이 경로를 처음부터 다시 통과
        rtl/frontend/rv_frontend.sv:181   request_slot_available = !outstanding_q || 응답 완료
        분기가 나가기 직전에 순차 다음 블록 요청이 이미 outstanding -> 타깃 요청은 그 응답이 돌아와야 발사
        -> 4 cycle fetch 경로를 다시 통과 -> 디코드 공백 5~6 cycle.
        (실제 사례: 사이클 200069 에 predicted-taken, 200072 에 타깃 요청 발사, 200077 에 첫 명령 디코드)
  (3) MMU 빌드에서는 FTB 가 꺼져 있다
        rtl/rv_ooo_core.sv:279   .ENABLE_TARGET_BUFFER(!HAS_MMU)   (최초 import 때부터, 설명 주석 없음)
        RV64 모델은 HAS_MMU=1 이라 FTB 적중 0회. RV32 기준선(HAS_MMU=0)은 FTB 가 켜져 있고 fetch 변환 FSM 도 없다 (사실).
        RV32 캐시 구조 IPC 1.12 와 RV64 0.61 의 차이에서 이 두 가지가 차지하는 비중은 직접 분리 측정하지 않았다 (추정).
        단, FTB 는 가상 타깃을 물리주소처럼 조회하므로(rv_frontend.sv 의 prediction_lookup_paddr) 그냥 켜면 안 되고
        MMU 안전한 형태(VA 태그, 권한/ASID 문맥 무효화)로 재설계해야 한다.

   변경 내용과 근거 (RTL 위치)
   (a) FTB 가 분기 예측 실패 복구마다 통째로 지워진다: rv_frontend.sv 의 FTB invalidate_i(redirect_valid_i).
       79 명령마다 비워져 FTB 크기를 키워도 효과가 없었다(16/64/128 동일). trap/fence.i/CSR 변경(flush_all)에서만 지우면 적중 77% -> 99%.
   (b) 분기 예측 실패 redirect 가 translate 유닛을 halt 시켜(rv_ooo_core.sv .halt_i(... || redirect_valid ...)) 복구 요청이 1 cycle 늦게 수락된다.
       권한/satp/PMP 가 바뀌지 않는 분기 복구에는 불필요 (제거 시 -1.2% cycles).
   (c) D-cache 쓰기: 쓰기 1건이 엔진+포트를 7 cycle 점유(cache 엔진 -> bridge(단일 outstanding) -> AXI AW/W -> SRAM bridge -> SRAM -> B).
       SB drain 이 로드보다 우선이라 앞선 store 가 포트를 막아 list_reverse 루프(ld/sd)가 반복당 8 cycle(이상 4) 걸렸다.
       posted write queue(port 0, 4칸): 쓰기를 즉시 받아 포트를 풀고, 엔진이 순서대로 버스에 내보낸다. 버스 응답이 와야 해당 SB 항목에 완료를 돌려주므로
       "write-through 완료는 시스템 버스 응답 대기" 규칙은 유지된다. 같은 word 로드는 큐에 남아 있는 동안 막고, MMIO/uncached/port 1 쓰기는 큐가 빌 때까지 기다려 순서를 지킨다.
       오류 응답 시 해당 line 무효화는 기존 동작을 유지했다.
   (d) bridge(rv_local_to_axi_bridge): 쓰기 요청 수락 cycle 에 AW/W 를 바로 올리고, B 응답을 레지스터 없이 CPU 로 전달 -> 쓰기 1건 7 -> 5 cycle.
   (e) FTB 적중 시 다음 순차 블록 요청이 1 cycle 늦게 나가 큐가 비던 문제: 적중 cycle 에 바로 요청 (rv_frontend 의 "적중 시 메모리 요청 억제" 가정을 바꿈).
   참고: 쓰기를 SRAM 에 직접 반영하는 이상화 모델(상한)은 1.182 였다. posted write queue 로 그 상한을 실제 RTL 로 넘어섰다 (⑦ 의 다른 개선 포함).

   효과 없던 시도 (같은 베이스 대비 cycles 변화 0~1% 이내, 또는 악화)
       분기 체크포인트 8->16 (0.0%), retire 슬롯1 load 커밋 허용 (0.0~0.1%), 로드/스토어 포트 우선순위 교대 (0.0%),
       cache 안 pending write 1칸 (-0.3%), 분기 태그/INT issue/ROB completion 파이프 단 제거 (-0.7~-5.9% 악화),
       응답 cycle 에 다음 쓰기를 바로 발행(cache+bridge chain): AXI mux 가 write_busy 동안 AW 를 막아 이득 없음 (AXI 프로토콜 assertion 위반도 확인)
   현재 남은 손실 (⑥ 기준 프로파일): 디코드 빈 사이클 11%, 분기 체크포인트로 dispatch 막힘 13.6% (증상: 늘려도 총 cycles 불변 — ROB/분기 해소 사슬 한계),
       load-use 사슬(core_bench_list IPC 0.78), 분기 예측 실패 7.5K 회(flush->첫 dispatch 3.5 cycle).

   회귀 검증 (사본 RTL, WSL Verilator)
       rv23_memory_tb (저장소 TB, 쓰기 큐 캐시 + 빠른 bridge): PASS checks=97 (기준선과 동일)
       rv23_cache_fault_tb: 데이터/오류/snoop/용량 검사 통과 (4,646 checks). 기준선 4,648 중 2개는 "쓰기 요청 수락 cycle 에 bus 요청이 나간다"는
         타이밍 계약이라 쓰기 큐 설계에서 의도적으로 달라 제외했고, "쓰기 완료를 같은 cycle 에 전달" 검사는 몇 cycle 대기 허용으로 완화했다 (TB 사본 사용).
       rv23_instruction_fetch_atomic_tb (저장소 TB, 전체 코어 + 사본 RTL): PASS offsets=16 (기준선도 PASS)
       rv23_cbo_head_tb (빠른 bridge): PASS checks=35
       if_translate_pa_tb (새로 작성, S-mode bare fetch 의 physical_address_o 검사): 원본 4000/4000 PASS, 수정 전 pass-through 4000/4000 불일치, 수정 후 PASS
       tohost 반복 쓰기 스핀 ELF (OpenSBI htif_system_reset 재현): 기준선 host-finish code=0, 수정 전 사본 AXI assertion 실패, 수정 후 host-finish code=0
       CoreMark 2/10회 전 구성 CRC 일치.

   부팅 회귀에서 발견한 결함 (Linux 6.12 + OpenSBI 재실행으로 발견, 둘 다 사본에서 수정)
       1) fetch pass-through 가 physical_address_o(pa_q) 를 갱신하지 않았다. rv_ooo_core.sv 는 이 값을 fetch PMP 검사 주소로 쓰므로 S-mode 첫 fetch(0x80200000)가
          stale 주소(0)의 PMP region(S 에 X 없음)으로 검사되어 instruction access fault -> OpenSBI 가 sbi_trap_redirect 를 무한 반복(약 5M cycle 부터 정지).
          M-mode 베어메탈 CoreMark 는 PMP 를 적용하지 않아 IPC 측정에서는 드러나지 않았다. 수정: bare pass-through 요청 수락 때 pa_q 에 요청 주소 기록. 사이클 변화 없음.
          수정 후 S-mode 진입이 3.69M cycle 에 일어나고(기준선 5.57M) trap 순서(0x80201048 page fault, ecall)가 기준선과 같다.
       2) 쓰기 큐 + bridge fall-through 로 core 의 store 가 SRAM bridge 에 빈틈 없이 도착하면, rv_axi_to_local_bridge 의 "쓰기 우선(ar_ready = IDLE && !aw_valid)" 때문에
          읽기(host 의 tohost 읽기, I-cache refill)가 굶는다. OpenSBI 의 htif_system_reset(tohost 를 무한 반복 쓰기)에서 부팅은 끝났지만 host 가 종료를 인식하지 못했고,
          스핀 ELF 재현에서는 I-cache AR 이 4096 cycle 정지하여 bridge 진행 timeout 이 AR 을 철회, rv_axi4_if 안정성 assertion 이 실패했다.
          수정: SRAM bridge 가 쓰기/읽기를 번갈아 허용(prefer_read_q). 기준선 쓰기 경로는 중간에 빈틈이 있어 문제가 드러나지 않았던 잠재 문제다.
       (참고) 부팅 첫 시도가 멈춘 것처럼 보였던 것은 RTL 이 아니라 모델을 tohost/fromhost 주소 인자 없이 빌드해 host 가 기본 주소(0x80020000)를 폴링한 내 실행 오류였다.
       Linux 6.12 부팅 (수정 ① 만 반영한 사본): LINUX_RTL_U_RETIRE pc=0x100b0, "RV23 LINUX INIT PASS", "reboot: Power down" 까지 완주 (약 42.7M cycle, 기준선 약 51M).
          이 시점에 결함 ② 때문에 시뮬레이션이 종료되지 않았다. 두 수정을 모두 반영한 모델은 [host-finish code=0] 까지 완주했다 (9장 상단).

9. 한계와 주의
-------------------------------------------------------------------------------------
   - 모든 변경은 사본 RTL(ifdef EXP_*)이며 저장소는 수정/커밋하지 않았다. 설계 승인이 아니라 "이 구성이면 IPC 1.2 가 나온다"는 시뮬레이션 근거다.
   - [부팅 회귀 최종 결과] 두 수정을 모두 반영한 모델(/root/rva23_demo/rtl_wqp_fair)이 Linux 6.12 부팅을 끝까지 완주했다 (2026-11-23).
     LINUX_RTL_S_ENTRY pc=0x80200000 -> LINUX_RTL_U_RETIRE pc=0x100b0 -> "RV23 LINUX INIT PASS" -> "reboot: Power down" -> [host-finish code=0], EXIT 0.
     PASS rv_act4_program_tb commits=23,911,168 (기준선 23,559,639; HTIF 폴링/타이머 대기 명령 수가 타이밍에 따라 달라 같을 필요는 없음).
     종료 cycle 약 43.3M (기준선 약 51.9M, 약 16% 감소; 시뮬 종료 시각 442ms vs 521ms). 로그: whatif_v2/fair_boot.log
     이 부팅은 M/S/U 전환, Sv39 MMU, PMP, 타이머 인터럽트, HTIF 콘솔, 사본의 FTB/pass-through/쓰기 큐/bridge 변경이 함께 실행된 것에 대한 통과이며,
     RV32 회귀, fence.i/atomic 전용 테스트, Sail 비교, 타이밍(Fmax)을 대신하지 않는다.
   - 성능 측정은 bare M-mode 베어메탈 CoreMark(O2/O3 스칼라) 뿐이다. pass-through fetch 는 bare 주소(M-mode 또는 satp bare)에서만 켜지고, MMU 켠 상태에서는 기존 변환 FSM 을 쓴다.
     FTB 는 MMU 빌드에서도 켜 두었다(가상 주소 기준 조회, flush_all 때만 무효화). 이 가정은 Linux 부팅(S-mode, MMU)의 실행 결과로만 확인했다.
   - 안 돌린 것: RV32 기준선 회귀(run_all_rv32_checks/audit_rv32_release), fence.i·atomic·MMU·PMP 전용 방향성 테스트, Sail 비교, 쓰기 큐/FTB 경합 전용 테스트.
     pass-through 사본은 기존 if_translate 의 프로토콜 assertion 을 꺼 두었다. 쓰기 큐/bridge/SRAM bridge 변경은 RV32 빌드(HAS_MMU=0)가 같은 모듈을 쓰는 한 RV32 에도 영향을 주므로 적용 시 RV32 회귀가 필요하다.
   - 부팅 회귀에서 결함이 2건 나왔듯이, 사본의 정확성은 M-mode CoreMark 만으로 확인되지 않는다. 위 결함 외에 S/U-mode, 인터럽트, atomic 경합에서 드러날 문제가 더 있을 수 있다.
   - 쓰기 큐는 port 0 만 쓴다(port 1 은 PTW 와 공유하는 단일 outstanding 중재기를 통과). 큐 4칸, 같은 word 로드 차단은 보수적이다.
   - 타이밍(Fmax) 영향 미평가: pass-through fetch, bridge fall-through/B bypass, FTB-hit 요청 발행은 조합 경로를 늘린다. 합성/STA 는 하지 않았다.
   - 이 결과로 RVA23 준수나 타이밍/합성 sign-off 를 주장하지 않는다.
   - 이론 상한(6장)은 레지스터 의존성만 반영해 낙관적이다. 실제 1.21 은 그 상한(1.37~1.47)의 약 85% 이다.
   - 사이클 분해의 구간 분류(taken / 순차 / flush)는 직전 3 cycle 의 신호로 정한 규칙이며, 겹치는 원인은 한 항목에만 배정된다.
   - 벡터(RVV) 빌드는 이번 분석 대상이 아니다.
